# RE:CONFIG 구현 변경 규칙

## 목적

이 문서는 구현자가 현재 코드, ROOM 문서, 확정된 디자인과 사용자 요청 사이의 충돌을 처리하는 공용 절차다. 빠른 구현보다 플레이 경험의 일관성과 이미 합의된 규칙의 보존을 우선한다.

## 변경 전 확인

- 요청과 관련된 현재 코드, 해당 ROOM 문서, 공용 가이드, 연결된 디자인 문서를 먼저 확인한다.
- 요청이 기존 규칙을 변경하는지, 단순히 그 규칙 안에서 배치·수치·흐름을 조정하는지 구분한다.
- 문서와 코드가 다르면 임의로 한쪽을 정답으로 정하지 않는다. 차이와 실제 영향을 밝힌 뒤 사용자에게 확인한다.

## 상충 요청 재확인 규칙 (필수)

다음 중 하나라도 해당하면, 사용자가 직접 지시했더라도 바로 구현하지 않고 한 번 더 확인한다.

- 공용 규칙, ROOM 문서, 확정된 디자인·아트·입력·물리 계약을 깨거나 뒤집는 변경
- 기존 오브젝트의 기본 상호작용 대상, 충돌, 이동, 시각 피드백, 상태 유지 방식을 제한·확장·반전하는 변경
- 이미 해결된 퍼즐 경로를 막거나, 새 우회를 만들거나, 난이도·실패 비용·리셋 범위를 크게 바꾸는 변경
- 성능 최적화가 플레이어에게 보이는 정보, 범위, 타이밍, 충돌 결과를 바꾸는 변경
- 문서상 서로 연결된 수치·배치·표기 중 일부만 바꿔 문서와 실제 플레이가 어긋날 수 있는 변경

재확인 메시지에는 반드시 아래를 포함한다.

1. 기존 규칙 또는 확정 사항
2. 요청이 바꾸는 정확한 내용
3. 플레이·퍼즐·시각·성능에 미치는 구체적 영향
4. 유지안과 변경안
5. 변경을 진행해도 되는지 묻는 명시적 질문

예: “현재 스위치는 플레이어·박스·피스톤 플레이트가 모두 누릅니다. 박스 전용으로 바꾸면 플레이어와 피스톤이 더 이상 누르지 못해 이 경로가 막힙니다. 이 예외를 문서화하고 적용할까요?”

## 구현 원칙

- ‘퍼즐을 어렵게 만들기 위해’, ‘우회를 막기 위해’, ‘더 자연스러워 보여서’ 같은 구현자 판단만으로 기존 규칙을 예외 처리하지 않는다.
- 사용자 승인 전에는 제한 activator, 새로운 충돌 예외, 외형 재설계, 흐름 변경, 문서와 다른 수치 적용을 하지 않는다.
- 승인된 예외는 코드만 바꾸지 않는다. 변경 이유, 영향, 적용 범위를 공용 문서와 해당 ROOM 문서에 함께 기록한다.
- 요청이 기존 규칙과 충돌하지 않으면 불필요한 확인 없이 조사·구현·검증까지 진행한다.

## 확인 후 검증

- 변경한 코드와 ROOM ASCII, 오브젝트 메모, 풀이 흐름, 충돌·물리 주의사항을 함께 대조한다.
- 빌드 오류뿐 아니라 변경한 규칙이 기존 ROOM에 미치는 회귀를 확인한다.
- 검증 중 새 충돌이나 의도하지 않은 우회가 발견되면, 임의 보정 대신 영향과 선택지를 사용자에게 보고한다.
